# AI 작업 방식

이 저장소에서 AI에게 무엇을 맡기고 무엇을 코드로 고정하는지, 그리고 그 작업이
어떻게 기록되는지 적는다.

## 제품 안에서의 경계

인터뷰 진행 자체가 이미 이 경계 위에 있다.

| 맡기는 쪽 | 하는 일 |
|---|---|
| Claude | 서버가 허용한 질문 후보 최대 3개 중 하나를 고르는 것, 짧은 대화 반응 |
| 서버 결정론 코드 | 음성 인식, 정보 추출, 후보 생성과 걸러내기, 상태 전이, 근거 검증, 완료 판정, 평가 |
| Python 파이프라인 | 피처 94개 계산, 2축 점수, 조건부 질문 판정, 재평가 |

Claude 요청은 `selectedInfoCode`, `reaction`, `question` 세 필드로 제한하고 8초를
넘기면 서버 1순위 질문으로 이어간다. 애매한 것의 해석은 모델에 맡기고 판정과
계산은 규칙이 고정된 코드가 하므로, 같은 입력이면 언제 돌려도 같은 결과가 나온다.

시연 시나리오 작업도 같은 경계를 지켰다. 인터뷰 답변을 점수로 옮기는 규칙은
`src/domain/modeling-interview-mapping.ts`에 표로 고정했고, 점수 계산은 그대로
`modeling/scorecard.py`가 한다. 같은 계산을 TypeScript로 다시 만들지 않았다.

## 작업 방식

### 계획 먼저, 승인 뒤 구현

파이프라인이나 화면을 바꾸는 작업은 구현 전에 다음을 확정하고 승인을 받는다.

1. 지금 구조가 어떻게 되어 있는지 (읽은 파일과 확인한 사실)
2. 무엇을 바꾸는지, 바뀌는 파일이 어디인지
3. DB 스키마와 API 계약에 영향이 있는지
4. 어떤 테스트로 확인할 것인지
5. 하지 말아야 할 작업이 무엇인지

5번을 계획에 넣는 이유는, 범위를 벗어난 변경이 대부분 "하는 김에"에서 나오기
때문이다. 시연 시나리오 작업의 계획에는 "2축 스코어카드를 TS로 재구현하지 않는다",
"Python이 없을 때 점수를 추정해 채우지 않는다", "기존 8항목·11항목 흐름을 바꾸지
않는다"를 미리 적었고 그대로 지켰다.

### 역할 분리

한 사람이 만들고 같은 사람이 검토하면 놓친 것을 그대로 통과시킨다. 그래서 세
역할을 나눈다.

| 역할 | 하는 일 | 하지 않는 일 |
|---|---|---|
| Researcher | 코드와 데이터를 읽어 사실을 모은다. 값은 실행해서 확인한다 | 설계하지 않는다 |
| Planner | 바꿀 것과 바꾸지 않을 것, 검증 방법을 정한다 | 구현하지 않는다 |
| Reviewer | 결과가 기준을 통과하는지 판정한다 | **코드를 고치지 않는다** |

Reviewer가 코드를 고치면 검증이 아니라 구현의 연장이 된다. 그래서 이 규칙을 사람의
약속이 아니라 코드로 고정했다. `scripts/verify-demo-scenario.mjs`는 통과와 실패만
찍고 어떤 파일도 쓰지 않는다. 실패하면 무엇이 어긋났는지 알리고 멈춘다.

같은 방식이 저장소 곳곳에 이미 있다.

| 검증기 | 판정하는 것 |
|---|---|
| `modeling/validate.py` | 케이스별 기대값, 깨진 입력, 밟지 않은 규칙 목록 |
| `modeling/doc_contract.py` | 문서의 피처 이름·경계 숫자와 코드가 같은지 |
| `tests/contracts/openapi.test.ts` | 실제 route와 문서화된 API가 같은지 |
| `scripts/e2e-smoke.mjs` | 인증부터 FINAL·평가까지 한 번에 도는지 |
| `scripts/verify-demo-scenario.mjs` | 시연 대본이 실물로 끝까지 도는지 |

### 사실 확인

문서나 답변에 숫자를 쓰기 전에 실행해서 확인한다. 시연 시나리오의 78.0과 67.5,
30.0은 전부 `modeling.scorecard`를 돌려 얻은 값이고, 재평가의 23.7에서 30.7도
`modeling.reevaluate` 출력이다. 확인하지 못한 값은 쓰지 않는다.

## 기록

작업마다 무엇을 요청받았고, 어떤 파일을 읽었고, 어떤 명령을 실행했고, 계획이
어디에서 왜 바뀌었는지 남긴다. 계획이 바뀐 지점을 특히 남긴다. 처음 판단이 틀렸던
자리가 나중에 같은 실수를 막아 주기 때문이다.

데이터와 로직 오류는 `tasks/lessons.md`에 따로 쌓는다. 두 기록 모두 저장소에
올리지 않는 로컬 문서다.
