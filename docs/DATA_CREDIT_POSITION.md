# 신용 포지션 축 (CreDB)

`external-data/credit_position.json` v0.1.0.

## 왜 별도 축인가

`peer_benchmark.json`(`ext_*` 12필드)은 **매출·비용·상권**을 다룹니다.
CreDB에는 그 데이터가 하나도 없습니다. 대신 CreDB만 줄 수 있는 것이 있습니다 —
**채무·연체·카드 이력**입니다.

앱의 `crd_*` 15필드가 정확히 그 영역입니다. 그래서 CreDB는 `ext_*`를 채우는 데 쓰지 않고,
**사장님이 인터뷰에서 말한 `crd_*` 값을 "어디쯤인가"로 환산하는 참조 분포**로 씁니다.

```
사장님: "대출 5천만원 정도 있어요"
   ↓  crd_total_debt = 50000 (천원)
   ↓  credit_position.json 조회
AI:   "전체 하위 67%, 또래 40대 중에선 하위 62%입니다"
```

두 축은 서로를 대체하지 않고 채워줍니다.

| 축 | 원천 | 답하는 질문 |
|---|---|---|
| 사업 (`ext_*`) | 서비스업동향조사 · 상권정보 (예정) | 동종업종 대비 매출·비용이 어디쯤인가 |
| 신용 (`crd_*`) | CreDB | 채무·연체·이력이 어디쯤인가 |

## 가장 중요한 주의

**원천이 신용정보원 '모의DB'입니다.** 스키마는 실물 CreDB와 같지만 값은 가상입니다.

- 분위수의 **절대 수준을 실증 근거로 인용하면 안 됩니다.**
- 쓸 수 있는 것은 **위치 산출 로직의 검증과 연동 설계**입니다.
- 실물 접근이 열리면 **같은 스크립트로 재생성**해 값만 교체합니다. 구조는 그대로입니다.

artifact의 `status`가 `mock_source`이고 `critical_caveat`에 같은 내용이 박혀 있습니다.

## 설계에서 짚은 세 가지

### 1. 업권코드 의미는 금리로 역산했습니다

CreDB의 `SCTR_CD`가 무엇인지 코드북 없이는 알 수 없습니다.
(`신용정보원_AI학습장_DB이용자매뉴얼_2024.pdf`에 있으나 현재 환경에 PDF 추출 도구가 없습니다.)

대신 **SDB의 `P_LN`에 `SCTR_CD`와 실행금리 `RATE`가 함께 있습니다.** 업권별 평균금리를
실측했습니다.

```
12  2.81%    01  4.56%    03  4.75%    06  4.95%
15  6.18%    17  7.57%    08  7.92%    16  8.31%
21 15.41%    05 15.94%   ← 고금리
```

임계 10%로 그어 `05`, `21`을 고금리 업권으로 판정합니다. 기관 종류를 이름으로 부르지 않고
**금리 수준으로만** 정의하므로 코드북 없이도 방어됩니다.

**가정:** SDB와 CreDB가 같은 업권코드 체계를 쓴다고 봅니다. 둘 다 신용정보원 산출물이고
코드 집합이 겹치지만, 코드북으로 확인된 것은 아닙니다. artifact에 `가정`으로 명시했습니다.

### 2. 0에 몰린 지표는 백분위가 무의미합니다

연체 횟수는 표본의 **93%가 0**입니다. 이 분포에서 전체 분위수는 p10=p50=p90=0이라
백분위 환산이 아무것도 구분하지 못합니다. 연체 없는 사장님에게 "상위 0%"라고 답하면 안 됩니다.

바닥 비율이 30% 이상인 지표는 **바닥 비율과 조건부 분포를 나눠서** 냅니다.

```
연체 0회  → "표본의 93%가 동일하다 — 변별 구간이 아니다"
연체 2회  → "0 초과 집단 내 하위 78%"   (n=143 안에서의 위치)
```

### 3. '상위 n%'라는 표현을 쓰지 않습니다

백분위는 **값의 크기 순서**일 뿐입니다. `crd_credit_history_months`처럼 클수록 좋은
지표에서 값이 작으면 하위인데, 이를 "상위 96%"로 뒤집어 부르면 양호하다는 뜻으로 읽힙니다.

그래서 위치는 항상 **"하위 n% — n%가 이보다 낮다"**로만 말하고,
좋고 나쁨은 `direction`으로 따로 붙입니다.

```
negative_is_improvement  →  부담이 큰 쪽 / 작은 쪽
positive_is_improvement  →  두터운 쪽 / 얇은 쪽
context_only             →  중립 지표
```

## 사용

```bash
python3 external-data/credit_position_lookup.py --demo
python3 external-data/credit_position_lookup.py crd_total_debt 50000 --age 40대
python3 external-data/credit_position_lookup.py crd_total_debt 50000 --age 40대 --json
```

```
기준월 총 대출잔액: 50,000 천원
  전체 하위 67% — 전체의 67%가 이보다 낮다  (중간 구간, n=1021)
    참조  p25 7,800 / p50 22,600 / p75 81,000
  또래(40대) 40대 하위 62% — 40대의 62%가 이보다 낮다  (중간 구간, n=284)
```

`--json`은 서비스가 그대로 소비할 형태로 냅니다.
스크립트는 표준 라이브러리만 쓰고, artifact를 같은 폴더에서 먼저 찾습니다.

## 배선이 아직 없습니다

**이 데이터는 `ext_*` 계약에 들어가지 않습니다.** `ExternalContextFeatureInput` 12필드에는
신용 관련 항목이 없습니다. 인터뷰 화면에서 사장님에게 위치를 되돌려주는 용도이며,
`peer_benchmark.json`과는 전달 경로가 다릅니다.

앱에 배선하려면 **별도 통로가 필요합니다.** 어떤 형태가 좋을지 알려주시면 그 형태로
맞추겠습니다. 지금은 `--json`으로 조회 가능한 상태까지 만들어 두었습니다.

`crd_*` 필드는 카탈로그상 **승인된 신용 원천이 있을 때만** 채워지므로, 이 분포를
사장님 진술의 위치 환산에 쓰는 것과 `crd_*`를 피처로 채우는 것은 다른 문제입니다.
전자만 의도한 것입니다.
