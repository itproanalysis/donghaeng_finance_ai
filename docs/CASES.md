# 검증 케이스

실제 고객 데이터가 아직 0건이라, 계산 로직을 검증하고 데모에 쓰기 위해 만든 mock
케이스 10개이다. 케이스 하나는 가상 사장님 한 명이다. 그 사장님의 카드매출 12개월,
계좌 6개월, 카드 사용내역, 서류, CB 조회, 인터뷰 답변까지 심사에 들어오는 데이터
전부가 data/mock/ 아래 폴더 하나에 들어 있다. modeling/make_mock.py가 시드 고정으로
만들므로 누가 몇 번을 돌려도 같은 값이 나온다.

케이스는 통계 표본이 아니다. "이 입력이면 이 결과가 나와야 한다"를 하나씩 고정해
두는 검증 사례라서, 로직이 설계대로 작동한다는 증거이지 점수가 현실을 예측한다는
증거가 아니다.

각 케이스의 "확인하는 것"은 전부 `python -m modeling.validate`의 자동 검사로
들어가 있다. 눈으로 보고 판단하는 항목은 없다.

| 번호 | 케이스 | 사장님 상황 | 확인하는 것 |
|---:|---|---|---|
| 1 | case_customer_drop | 손님이 줄어 매출 -20% | 하락 원인이 "손님 감소"로 계산되는지 |
| 2 | case_ticket_drop | 가격을 내려 매출 -20% | 하락 원인이 "가격 인하"로 계산되는지 |
| 3 | case_operating_drop | 문 연 날이 줄어 매출 -20% | 문을 왜 닫았는지 묻는 질문이 추가되는지, 그 답으로 점수가 오르는지 |
| 4 | case_operating_drop_after | 3번 사장님의 6개월 뒤 | 목표를 이뤘는지 같은 방식으로 다시 계산되는지 |
| 5 | case_no_answer | 3번과 같은 데이터인데 인터뷰에 답을 안 함 | 답이 없으면 점수가 내려가는지 |
| 6 | case_cost_pressure | 매출은 그대로인데 새 대출로 고정비가 늘어남 | 고정비와 잔액 질문만 추가되는지 |
| 7 | case_demand_shift | 매출은 그대로인데 배달과 주중으로 손님이 옮겨감 | 매입, 배달, 요일 질문만 추가되는지 |
| 8 | case_interior | 9주치 계약이 잡혀 있는 인테리어 가게 | 잡혀 있는 계약이 점수에 반영되는지 |
| 9 | case_volatile | 여름에 매출이 몰리는 가게 | 매출이 심하게 오르내리면 방향 점수를 빼고 계산하는지, 성수기 진술이 실제와 맞는지 |
| 10 | case_new_low | 12개월 내내 줄어 지금이 제일 낮음 | 현재 상황 점수가 0점까지 내려가는지 |

## 원인 구분 3개

세 케이스는 3개월 평균 매출이 똑같이 -20%이고 계좌, 카드지출, 서류, CB 파일이
동일하다. 피처와 점수 차이가 매출 하락의 원인에서만 나오게 하기 위해서이다.
원인이 다르면 사장님이 할 일이 다르므로, 이 구분이 제품이 푸는 문제이다.

- **1. case_customer_drop** 결제 건수만 20% 줄인 가게. 손님이 빠진 하락이다.
  하락 원인이 손님 감소로 계산되는지, 영업일 질문이 나오지 않는지 확인한다.
- **2. case_ticket_drop** 손님 수는 그대로인데 한 명이 내는 금액만 20% 줄어든 가게.
  가격을 내려 버티는 하락이다. 하락 원인이 1인당 결제액 하락으로 계산되는지 확인한다.
- **3. case_operating_drop** 문 연 날만 20% 줄인 가게. 인터뷰에서 사유를
  "건강, 지금은 해소됨"으로 답한다. 영업일 질문이 이 케이스에서만 나오는지,
  그 답으로 개선가능성 점수가 앞 두 케이스보다 높아지는지 확인한다.

## 재평가 1개

- **4. case_operating_drop_after** case_operating_drop의 6개월 뒤. 영업일이 회복된
  거래 데이터만 있고 인터뷰 파일이 없다. 재평가가 같은 계산 함수로 도는지,
  인터뷰 피처가 0이 아니라 MISSING으로 남는지 확인한다.

## 인터뷰 무응답 1개

- **5. case_no_answer** case_operating_drop과 거래 데이터가 완전히 같고 인터뷰 답만
  다르다. 영업일 질문을 받았지만 사유를 답하지 않았고, 다시 물어도 목표값과 기간,
  예산을 정하지 못했다. 매출 방향이 0점(하락, 사유 없음), 계획의 현실성이
  0점(목표 안 정함)으로 내려가 개선가능성이 원인 구분 3개보다 낮아지는지
  확인한다. 같은 데이터에서 답만 달라 점수가 달라지는 것이 인터뷰가 하는 일이다.

## 추가 질문 2개

- **6. case_cost_pressure** 매출은 평탄한데 최근 3개월에 새 대출 상환이 붙어 반복
  출금이 늘었고, 시작 잔액이 낮아 잔액이 그달 고정비에 못 미치는 날이 이어진다.
  고정비 질문과 잔액 질문만 나오고 나머지 넷은 나오지 않는지 확인한다.
  현재 상황 축이 낮게 나오는 케이스이기도 하다.
- **7. case_demand_shift** 매출은 평탄한데 최근 3개월에 배달 비중이 35%로 오르고,
  주중 매출 비중이 12%p 오르고, 매입 지출이 25% 늘었다. 매입, 배달, 주중 질문
  셋만 나오는지 확인한다. 목표 1인당 결제액을 현재의 1.5배 위로 잡아 계획의
  현실성이 낮은 구간으로 내려가는 것도 같이 본다.

## 업종과 계절 2개

- **8. case_interior** 업종이 INTERIOR이고 9주치 계약과 계약금이 잡혀 있다.
  잡혀 있는 계약 항목이 해당 없음으로 제외되지 않고 20점으로 산출되는지 확인한다.
- **9. case_volatile** 여름에 매출이 몰리는 가게이다. 성수기 월매출이 4천6백만원,
  비수기가 8백만원이고 최근 6개월 창에 둘이 함께 들어와 매출 변동계수가 0.5를
  넘는다. 매출 방향과 저점 회복이 제외되고 "매출 오르내림이 커서 방향 판단 제외"가
  붙는지, 남은 항목만으로 100점 환산이 되는지 확인한다. 사장님이 말한 성수기(6~8월)와
  실제 매출 피크 달이 맞는지도 같이 본다.

## 계속 하락 1개

- **10. case_new_low** 12개월 내내 매출이 줄어 마지막 달이 제일 낮고, 매출이
  줄어든 뒤에도 상환액은 그대로이다. 저점 회복이 "지금이 제일 낮음"으로 0점이 되는지,
  현재 상황 5항목이 전부 0점이 되는지 확인한다. 축 전체가 0점인 유일한
  케이스이다.

## 깨진 입력

정상 케이스를 복사해 입력을 망가뜨리고, 계산이 조용히 틀린 값을 내지 않는지 본다.
`modeling/broken_inputs.py`에 있고 결과는 validate 출력에 함께 찍힌다.

| 망가뜨린 것 | 기대 |
|---|---|
| 빈 카드매출 파일 | 죽지 않고 계산 불가 자리가 전부 결측 상태 |
| 빈 계좌 파일 | 죽지 않고 계산 불가 자리가 전부 결측 상태 |
| 배달 매출 열 누락 | 예외로 멈춤. 없는 열을 0으로 채우지 않음 |
| 3개월 이력만 | 죽지 않고 6개월, 12개월 창이 필요한 피처가 MISSING |
| 날짜 뒤섞임 | 정렬 전후 피처 94개가 완전히 일치 |

## 규칙 단위 검사

케이스는 "이 입력이면 이 결과"를 고정하지만, 그 케이스가 밟지 않는 경로는 규칙이
뒤집혀도 통과한다. 그래서 `modeling/rule_checks.py`가 규칙 함수에 값을 직접 넣어
확인한다. 케이스가 하나도 없어도 돌고, 아래 규칙이 뒤집히면 바로 깨진다.

| 검사 | 막는 것 |
|---|---|
| 잡혀 있는 계약, 계약금이 감점이 아님 | 계약금을 받은 사장님이 못 받은 쪽보다 낮은 점수 |
| 잡혀 있는 계약, 주 수에 단조 | 계약이 늘었는데 점수가 내려가는 것 |
| 적자면 부담 비율 분모로 안 씀 | 적자 가게가 "예산 부담 없음"으로 읽히는 것 |
| 버틸 수 있는 일수가 음수 아님 | 잔액이 마이너스일 때 음수 일수 |
| 안 정함과 안 물어봄을 구분 | 인터뷰를 안 한 것을 "목표 안 정함" 0점으로 처리 |
| 성수기는 진짜 피크일 때만 | 평탄한 매출과 하락 추세를 성수기로 읽는 것 |
| 일손 해소는 데이터로 대조 | 사람을 구했다는 진술만으로 6점이 오르는 것 |
| 업종 코드는 enum 안에서만 | 11개 밖의 값이 업종으로 들어오는 것 |
| 경계가 같으면 부호만 봄 | 기울기 0을 상승으로 읽는 것 |

## 규칙 커버리지

validate는 케이스 10개와 깨진 입력을 다 돌린 뒤, 조건부 질문 6개마다 나오는
케이스와 안 나오는 케이스가 둘 다 있는지, 스코어카드의 구간 52개 중 어느 케이스도
밟지 않은 것이 무엇인지 출력한다.

지금 조건부 질문은 6개 전부 양쪽 사례가 있고, 스코어카드는 52개 중 39개 구간이
실행된다. 남은 13개는 밟는 케이스가 아직 없다. 그 목록을 코드
(`modeling/validate.py`의 `BANDS_WITHOUT_CASE`)에 적어 두고 실제 미실행 목록과
정확히 같은지 검사한다. 케이스를 늘리거나 규칙을 고쳐 목록이 달라지면 검증이
깨진다.

| 항목 | 케이스 없는 구간 |
|---|---|
| 잔액 부족일 | 1~2일, 3~5일 |
| 매출 대비 상환 부담 | 10~20% |
| 버틸 수 있는 일수 | 15~29일 |
| 저점 회복 | 회복 중 |
| 잡혀 있는 계약 | 4주 이상 계약금 미확인, 4주 미만, 없음 |
| 비용 줄일 여지 | 15~30%, 5~15%, 5% 이하 |
| 계획의 현실성 | 목표가 데이터와 어긋나 한 구간 아래인 두 경우 |

점수 0점 구간 중에는 잡혀 있는 계약의 "없음"과 비용 줄일 여지의 "5% 이하"만 남았다.
나머지는 중간 구간이라 밟으려면 케이스를 그만큼 더 만들어야 한다. 확인할 것이
분명하지 않은 케이스는 수를 늘려도 증거가 되지 않으므로 만들지 않았고, 대신
무엇이 실행된 적 없는지를 이렇게 적어 둔다.

## mock의 한계

케이스는 손으로 설계한 입력이라 실제 가게 데이터가 아니다. 지금 남아 있는
어긋남을 적어 둔다.

- 잔액이 바닥날 때의 대처 답(`own_low_balance_coping_method`)을 "그냥 버팀"으로
  둔 것은 계좌에 추가 자금이 들어온 흔적이 없기 때문이다. 카드론이나 추가 대출로
  답하면 계좌에 그 입금이 찍혀야 하는데 mock에는 없다
- case_cost_pressure의 새 고정 지출 금액(월 450만원)은 반복 출금 탐지가 변동
  지출과 섞이지 않는 금액대를 골라 정했다. 실제 대출 규모에서 나온 값이 아니다
- 배달 비중 35%와 주중 비중 12%p 변화는 질문이 나오는 기준을 넘기려고 정한 값이다.
  이 수치가 실제 음식점에서 흔한지는 확인하지 못했다
