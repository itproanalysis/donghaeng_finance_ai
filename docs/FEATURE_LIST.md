# 인터뷰 데이터 피처

## 푸는 문제

카드매출이 석 달째 20% 내려간 가게 두 곳이 있어도 거래 데이터에는 같은 모양으로
남는다. 한 곳은 사장님이 아파서 문을 못 연 동안 생긴 하락이고, 다른 곳은 손님이
계속 빠지는 중이다. 앞은 끝난 일이고 뒤는 진행 중이라 사장님이 할 일도 심사가 볼
것도 다른데, 그 이유가 거래 데이터에는 남지 않는다.

그래서 데이터에서 물어볼 자리를 먼저 찾고, 인터뷰로 이유를 받아 데이터 옆에 붙인다.
이 문서는 그렇게 만든 피처 94개의 이름과 정의이며, 제품 코드의 registry도 이 문서를
따른다.

## 한눈에

| 데이터 소스 | 피처 수 |
|---|---:|
| 카드매출 12개월 | 18 |
| 계좌 입출금 6개월 | 18 |
| 카드 사용내역 12개월 | 5 |
| 제출 서류 | 6 |
| CB 연계 | 1 |
| 인터뷰 | 30 |
| 여러 소스 조합 | 16 |
| 합계 | 94 |

코드명 앞머리

| 앞머리 | 뜻 |
|---|---|
| `fin_` | 돈. 매출액, 현금흐름, 잔액, 지출 |
| `ops_` | 손님과 영업. 손님 수, 1인당 결제액, 단골 |
| `biz_` | 사업체 규모와 매출 추세 |
| `own_` | 사장님이 말한 것 |
| `crd_` | 부채 |
| `imp_` | 여러 값을 합쳐 만든 개선가능성 |

## 사장님 동의 후 받아야 할 데이터

| 받을 것 | 어디서 | 무엇이 필요한지 |
|---|---|---|
| 카드매출 12개월 | 카드사 | 일별 매출액, 결제 건수, 배달 매출 구분 |
| 계좌 입출금 6개월 | 은행 | 일별 잔액, 입금, 출금, 거래 일자와 금액 |
| 카드 사용내역 12개월 | 카드사 | 결제처 업종, 금액, 일자 |
| 사업자등록증 | 사장님 제출 | 업종, 개업일, 사업장 수 |
| 임대차계약서 | 사장님 제출 | 임대료 |
| 부가세과세표준증명 | 사장님 제출 | 신고매출 |
| CB 조회 | CB사 | 점수, 등급, 상위 비율, 연체가능성, 월 상환액, 심사 의견 |
| 인터뷰 답변 | 사장님 본인 | 아래 인터뷰 항목 |

계좌는 6개월치, 카드는 12개월치를 받는다. 기간이 달라 12개월 흐름은 카드 쪽에서만
나온다. 거래 데이터를 인터뷰보다 먼저 받고, 데이터에서 이상한 자리를 찾아 인터뷰에서
이유를 묻는다.

줄어서인지 구분하는 조합이다. 셋은 사장님이 할 일이 서로 다르다.

| 반복 출금 비중 | `fin_recurring_outflow_ratio` | 나가는 돈 중 당장 손댈 수 없는 부분의 몫 |

| 잔액 부족일 수 | `fin_low_balance_day_count_3m` | 잔액이 그달 고정비에도 못 미치는 날의 수 |
| 잔액 오르내림 | `fin_balance_volatility_3m` | 잔액이 오르내리는 폭 |

반복 출금은 매달 비슷한 날짜(±3일)에 비슷한 금액(±10%)이 3번 이상 나가는 묶음으로
찾는다. 연속한 3개월이어야 하고, 아무 세 달로 잡으면 변동 지출이 우연히 걸린다.
받는 사람 이름은 보지 않으므로 상호가 흐릿하게 찍혀도 잡힌다.

버틸 수 있는 일수는 마지막 월말 잔액을 하루 유출로 나눈 값이고, 하루 유출은 월 유출
평균을 30으로 나눈다. 잔액 부족일은 일별 잔액이 그달 반복 출금 합계보다 낮은 날의
수이고 최근 3개월을 합산한다. 반복 출금이 하나도 안 잡히면 두 값 다 MISSING이다.

## 인터뷰 (30개)

인터뷰는 지금 한 번만 한다. 데이터에 안 남는 것을 채우고, 6개월 목표를 정한다.
6개월 뒤에는 인터뷰 없이 카드매출과 계좌를 다시 받아 목표 피처만 다시 계산한다.

문항은 최대 20개로, 항상 묻는 14개와 데이터가 조건에 걸릴 때만 묻는 6개가 있다.
문항 하나가 피처 여러 개를 만든다.

### 데이터에 안 남는 것 (16개)

#### 데이터를 보고 추가로 묻는 것 (7개)

조건에 걸린 사장님에게만 묻는다. 조건은 코드로 고정해 같은 데이터면 같은 질문이 나온다.

| 조건 | 묻는 것 | 피처 | 코드명 |
|---|---|---|---|
| 영업일이 줄었을 때 | 문 닫은 날이 늘어난 사정 | 사유 | `own_operating_day_drop_reason` |
| | | 지금은 해소됐는지 | `own_operating_day_drop_resolved_flag` |
| 고정비가 늘었을 때 | 새로 생긴 고정 지출 | 사유 | `own_fixed_cost_increase_reason` |
| 잔액이 바닥날 때 | 그 시기를 넘기는 방법 | 대처 | `own_low_balance_coping_method` |
| 매입이 늘었을 때 | 매입이 늘어난 사정 | 사유 | `own_purchase_increase_reason` |
| 배달 비중이 높을 때 | 플랫폼에 나가는 몫 | 수수료 부담 | `ops_platform_fee_ratio` |
| 주중 매출 비중이 변했을 때 | 홀 손님 변화 | 홀 손님 감소 | `biz_hall_customer_decline_flag` |

보기

| 피처 | 보기 |
|---|---|
| `own_operating_day_drop_reason` | 건강, 일손, 가족, 수요 감소, 사업 축소 |
| `own_fixed_cost_increase_reason` | 임대료 인상, 장비 리스, 보험, 신규 대출, 구독 |
| `own_low_balance_coping_method` | 카드론, 지인, 대금 미루기, 추가 대출, 그냥 버팀 |
| `own_purchase_increase_reason` | 원가 상승, 재고 확보, 메뉴 확대, 거래처 변경 |

답은 보기 중 하나로 저장하고 원래 문장도 근거로 보관한다.

질문이 나오는 기준은 아래와 같다. 전부 임시값이고 `modeling/thresholds.py`에 모여 있다.

| 조건 | 재료 | 질문이 나오는 기준 |
|---|---|---|
| 영업일 감소 | `biz_operating_day_change_3m` | -15% 이하 |
| 고정비 증가 | `fin_recurring_outflow_growth_3m` | +10% 이상 |
| 잔액 바닥 | `fin_low_balance_day_count_3m` | 최근 3개월 합쳐 3일 이상 |
| 매입 증가 | `fin_purchase_spend_growth_3m` | +20% 이상 |
| 배달 비중 | 최근 3개월 배달 매출 비중 | 30% 이상 |
| 주중 비중 변화 | `ops_weekday_sales_share_change` | 절댓값 10%p 이상 |

재료가 MISSING이면 질문을 만들지 않는다. 없는 값을 조건에 걸린 것으로 읽지 않기 위해서이다.

영업일 감소는 카드 데이터에 남지만, 아파서 못 연 것과 손님이 없어 안 연 것이 똑같이
보인다. 둘은 개선가능성이 반대이고 물어야만 나뉜다.

|---|---|---|

#### 계절 (2개)

| 피처 | 코드명 | 설명 |
|---|---|---|

| 매출 진술 일치도 | `fin_sales_consistency_score` | 진술, 카드매출, 신고매출 셋이 얼마나 벌어져 있는지 |
| 성수기 진술 일치 | `biz_seasonality_statement_match` | 말한 성수기와 실제 매출 피크 달이 맞는지 |

주중은 월요일부터 금요일까지이다.

성수기 진술은 실제 매출 상위 3개월과 겹치는 달이 하나라도 있으면 일치로 본다. 다만
아래 두 경우에는 대조하지 않고 MISSING으로 둔다. 12개월치로는 계절과 추세를 구분할
수 없으므로, 구분이 안 되는 데이터에서 대조하면 계절이 아닌 것을 두고 진술이
틀렸다고 표시하게 된다.

- 상위 3개월 평균이 12개월 평균의 1.2배에 못 미치면 성수기가 없는 가게로 본다.
  평탄한 매출에서 상위 3개월은 잔흔들림일 뿐이다
- 계절로 몰린 폭이 12개월 추세로 설명되는 폭보다 크지 않으면 추세로 본다.
  매출이 내내 줄어든 가게의 상위 3개월은 성수기가 아니라 덜 나빴던 과거이다

대조 결과는 판정이 아니라 상담사가 한 번 더 확인할 자리의 표시이다.
현금 장사가 많으면 카드매출이 낮게 잡히므로 벌어지는 것이 정상이다.

### 개선가능성 (7개)

| 피처 | 코드명 | 설명 |
|---|---|---|
| 회복하고 있는가 | `imp_recovery_momentum` | 매출 증가율, 현금흐름 추세, 잔액 증가를 합친 최근 방향 |
| 현금흐름이 안정되나 | `imp_cashflow_stabilization` | 흑자월 비율, 적자월 수, 잔액 증가를 합친 신호 |
| 매출이 되살아날 여지 | `imp_sales_recovery_potential` | 저점 대비 회복, 단골 비중, 매출 증가율을 합친 신호 |
| 잡힌 계약이 몇 주치인가 | `imp_future_demand_visibility` | 잡혀 있는 계약 금액과 기간을 평균 매출로 견준 값 |
| 비용 줄일 여지 | `imp_cost_adjustment_headroom` | 나가는 돈에서 반복 출금을 뺀 몫. 업종 평균 자료가 필요 없는 방식 |
| 계획 실현 가능성 | `imp_plan_feasibility` | 목표 배수와 예산 부담으로 본 실현 여지 |
| 목표와 데이터가 맞나 | `imp_goal_data_alignment` | 데이터가 가리키는 문제와 사장님이 꼽은 문제, 고른 목표가 맞는지 |

`imp_cost_adjustment_headroom`만 비율(유출에서 반복 출금을 뺀 몫 ÷ 유출)로 내고,
나머지 6개는 재료마다 방향 신호(+1, 0, -1)를 붙여 가중치 없이 더한 값과 쓴 재료 수를
같이 남긴다. 어느 재료가 더 중요한지 정할 근거가 없어 가중치를 두지 않는다.
쓸 재료가 하나도 없으면 MISSING이고, 잡혀 있는 계약이 없는 업종의
`imp_future_demand_visibility`는 NOT_APPLICABLE이다.

방향 신호 경계는 아래와 같다. 전부 임시값이고 `modeling/thresholds.py`에 모여 있다.

| 재료 | -1 | +1 |
|---|---|---|
| 매출 증가율 | -5% 이하 | +5% 이상 |
| 현금흐름 추세 기울기 | 음수 | 양수 |
| 잔액 증가율 | -5% 이하 | +5% 이상 |
| 흑자월 비율 | 50% 이하 | 80% 이상 |
| 적자월 수 | 3개월 이상 | 1개월 이하 |
| 저점 대비 회복률 | +5% 이하 | +30% 이상 |
| 단골 비중 | 20% 이하 | 40% 이상 |
| 잡혀 있는 계약 금액 ÷ 평균 매출 | 0.3 이하 | 1.0 이상 |
| 잡혀 있는 계약 기간 | 4주 이하 | 8주 이상 |
| 목표 배수 | 2.0배 이상 | 1.5배 이하 |
| 예산 부담 | 2.0배 이상 | 1.0배 이하 |

기울기는 단위가 없어 경계를 정할 수 없으므로 부호만 본다.

`imp_goal_data_alignment`는 경계가 아니라 대응 관계로 신호를 낸다. 매출 하락의
원인마다 대응하는 목표 피처와 `own_primary_problem` 보기를 정해 두고, 사장님이
고른 것이 거기에 맞으면 +1, 아니면 -1이다.

| 하락 원인 | 대응하는 목표 피처 | 대응하는 제일 큰 문제 |
|---|---|---|
| 손님 수 | `ops_transaction_count_avg_3m` | 손님 감소 |
| 1인당 결제액 | `ops_avg_ticket_3m` | 단가 압박 |
| 영업일 | `biz_operating_day_count_avg_3m` | 해당 보기 없음 |

원인이 영업일일 때는 맞는 `own_primary_problem` 보기가 없어 목표 피처만 본다.
원인이 하나로 안 나뉘거나 하락이 아니면 MISSING이다.

## 업종 벤치마크

같은 업종의 다른 가게와 견주는 값은 데이터 담당이 만든 `external-data/peer_benchmark.json`
에서 받는다. 업종 11개 x 12필드이고 KOSIS 서비스업생산지수 기반으로 9업종이 채워져 있다.

이 12필드는 피처 94개에 들어가지 않고 점수에도 쓰지 않는다. CB 심사 의견 옆에 나란히
놓는 대조 재료로만 쓴다. 외부 파일의 `null`은 `MISSING`으로 그대로 옮기고 0으로 채우지
않으며, 파일이 없으면 12필드 전부 `MISSING`이다. 변환 규칙은 `modeling/README.md`에 있다.

변동성 두 필드는 절대 수준을 판단 재료로 쓰지 않는다. 업종 지수의 변동성이라 가게 한
곳의 변동성과 같은 자로 잴 수 없다.

## 값을 다루는 규칙

- 증가율은 0에서 1 사이로 누르지 않고 계산값 그대로 저장한다. 누르면 -50%와 -1%가
  같은 값이 된다
- 저점 대비와 고점 대비를 둘 다 둔다. 회복률만 보면 반토막 난 가게가 성장한 것으로
  읽힌다
- 없는 값은 0으로 채우지 않는다. 매출 0인 달과 데이터가 없는 달은 다르다
- 안 나온 항목은 다시 묻고, 그래도 안 나오면 "안 정함"으로 기록한다. 몇 개 답했는지는
  세지 않는다
- 계절 보정은 계산으로 하지 않고 인터뷰로 받는다. 계산하려면 24개월치가 필요한데
  12개월뿐이다
- 말솜씨를 점수로 만드는 피처는 두지 않는다. 감정, 목소리, 표정도 쓰지 않는다
- 추가 질문은 보기 중에서 고르게 하고 원문을 근거로 보관한다. 같은 답이면 같은
  값이 나온다

## 한계

- 자기진술은 답하는 쪽에 유리하게 기운다. 산출물은 검증된 사실이 아니라 추적 가능한
  진술이다
- `imp_` 7개와 스코어카드 점수의 예측력은 확인되지 않았다. 심사 참고자료로만 쓰고
  승인 판단에 쓰지 않는다
- 업종 평균과의 비교 피처는 같은 업종 데이터가 확보되기 전까지 만들지 않는다
- 등급 산출은 SCB(2026년 3분기 운영개시)의 영역이므로 하지 않는다
